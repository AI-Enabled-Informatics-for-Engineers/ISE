PART 01

The Production Reality Check

⏱ ~5 minutes

Huyen opens Chapter 9 with a deceptively simple statement: "No matter how good your model is, if it's too slow, your users might lose patience — or worse, its predictions might become useless."

She gives the example of a next-day stock price prediction model that takes two days to compute. A prediction that arrives after the decision window has closed is not late — it is wrong. Latency is a form of quality failure.

The ISE Version of This: A predictive maintenance model that detects a bearing failure in 45 seconds — but the operator's decision window is 30 seconds before cascade failure — is not a maintenance tool. It is a post-failure analysis tool. The insight is correct. The timing renders it useless.

Three Dimensions Every Production System Must Satisfy Simultaneously

⚡
Latency
Can it respond fast enough for the use case? Every operator decision has a time window.
💲
Cost
Can you afford to run it at production volume? $2/query × 1M queries/day = $2M/day.
🔁
Reliability
Can it handle burst loads, concurrent users, and variable input lengths without degradation?

NASA C-MAPSS: Our Running Dataset for This Week

The C-MAPSS (Commercial Modular Aero-Propulsion System Simulation) dataset simulates jet engine degradation across multiple operational cycles. It contains time-series sensor readings from 21 sensors per engine, across 4 operational conditions and 6 fault modes. The task: predict Remaining Useful Life (RUL) before failure — a canonical ISE prognostics problem.

DECISION WINDOW
Engine overhaul window: 50–100 flight cycles before predicted failure. Predictions must arrive before maintenance scheduling locks in.
SCALE
A commercial airline monitors 300+ engines simultaneously. Each query: 21 sensor features × 30-cycle window = ~1,800 data points per engine per query.
COST IF WRONG
CFM56 engine replacement: ~$12M. Unplanned removal: ~$500K in delays and crew disruption. Missing RUL by 10 cycles is real money.
Huyen's Archery Analogy: Model-level optimization = crafting better arrows. Hardware-level optimization = training a stronger archer. Service-level optimization = refining the entire shooting process — bow, stance, timing, conditions. This week covers all three layers.
PART 02

Computational Bottlenecks

⏱ ~8 minutes

Before you can optimize anything, you need to know what is actually slow. Optimization without diagnosis is guessing. There are two fundamental computational bottleneck types — and understanding them determines which optimization toolkit even applies to your problem.

⚡ Compute-Bound

The bottleneck is the number of calculations required. Fix: more FLOP/s. Examples: password decryption, image generation, the prefill phase of LLM inference — processing all input tokens simultaneously in parallel.

Fix → more chips, higher FLOP/s, better parallelization

📡 Memory Bandwidth-Bound

The bottleneck is data transfer speed — moving data between memory and processors. Fix: higher bandwidth. The decode phase of LLM inference is the textbook example: the entire model weights must be loaded from GPU memory for every single token generated.

Fix → HBM chips, quantization (fewer bytes/param), KV cache optimization
Critical fact for 2026: Due to transformer architecture dominance and current hardware limitations, most AI workloads are memory bandwidth-bound. The autoregressive decode loop — loading the entire model's weights for every single token — is the textbook case. This one fact drives most of the optimization techniques we will cover today.

The LLM Two-Phase Split

LLM inference has two phases with completely different computational profiles. This asymmetry is why optimization is hard and why treating them identically is inefficient.

PREFILL
All input tokens processed in parallel. Context-length driven. Fast.
Compute-bound ⚡
DECODE
One token generated at a time. Sequential. Loads full model weights per token.
Memory bandwidth-bound 📡
For your C-MAPSS system: A query processes the 21-sensor window + system prompt in prefill (fast, one-shot). Then generates the 80–120 token RUL explanation word-by-word in decode. That's where your operator waits. That's where to optimize.

Memory Hierarchy — Where the Data Lives

MemoryLocationBandwidthTypical SizeRole in Inference
CPU DRAMSystem memory25–50 GB/s16 GB–1 TB+Cold storage — model weights before loading to GPU
GPU HBMOn the GPU card256 GB/s – 1.5+ TB/s24–80 GBActive inference — weights and KV cache live here
GPU SRAM (on-chip)Inside the GPU die10+ TB/s~40 MBHot cache for current computation. FlashAttention exploits this.
The ISE Operations Analogy: Think: warehouse (CPU DRAM — huge, slow), production floor (GPU HBM — medium size, fast), workbench (SRAM — tiny, instant). You want active work on the workbench. Moving material from warehouse to floor is the bottleneck — that is memory bandwidth.

Online vs. Batch API — The Routing Decision

Online API — Optimize for Latency

Requests processed as they arrive. Streaming mode returns tokens as generated. Use when: operator chatbots, real-time alerts, interactive dashboards requiring immediate response. Cost: full price.

→ Real-time C-MAPSS alert: "Engine 47 RUL critical"

Batch API — Optimize for Cost

Requests processed in bulk with hours of turnaround. Use when: nightly fleet analysis, weekly reports, model migration reprocessing, scheduled summaries. Cost: 50% discount (OpenAI, Gemini as of 2024).

→ Weekly C-MAPSS fleet health summary

Design principle: Every use case has a different latency tolerance. Route accordingly. Operator asking "is this engine safe to fly tonight?" needs online API. Maintenance planner scheduling next quarter's fleet overhauls can use batch API and cut that workload's cost in half. One system, two endpoints, significant savings.
PART 03

Performance Metrics — What to Actually Measure

⏱ ~10 minutes + Demo 1

You cannot optimize what you do not measure. Before changing anything, instrument your system with the right metrics. Huyen defines a precise vocabulary — and each metric changes what you optimize for.

The Latency Decomposition

TTFT
Time to First Token
Duration of prefill. Driven by input length. For a chatbot: should feel instant. For a long document: users tolerate a few seconds.
TPOT
Time Per Output Token
Speed of the decode loop. Target: ~120ms/token (human reading speed). Total latency = TTFT + TPOT × (output tokens).
p99
Tail Latency
Your worst 1% of users. Average latency hides outliers. Always report p50, p90, p99. One 3,000ms request in 10 skews your average to 390ms.
The TTFT/TPOT tradeoff: Two systems with identical total latency offer different user experiences. An operator waiting for a C-MAPSS recommendation prefers instant first token (low TTFT) even if subsequent tokens arrive slightly slower — they can start reading while the rest generates. Design for the actual user experience, not just the aggregate number.

Throughput vs. Goodput

Throughput (tokens/s)

Raw generation rate across all users. Higher = lower cost per token. Directly linked to dollars. Can be 2–3× higher if you sacrifice some TTFT/TPOT. Useful for capacity planning but misleading as a user experience metric.

Goodput (requests/s meeting SLO)

Requests per second that actually satisfy your latency SLO. If you handle 100 RPS but only 30 meet TTFT < 500ms, goodput = 30 RPS. The only metric that genuinely reflects user experience.

The optimization trap: You doubled throughput — but your p99 TTFT tripled because the batch got bigger. Net result: worse user experience. Always track goodput alongside throughput. A system that looks efficient on dashboards and fails operators in the field is not a success.

Utilization: MFU and MBU

The nvidia-smi gotcha: nvidia-smi's GPU utilization metric shows the percentage of time the GPU is doing something. A GPU doing 1 operation/second out of a possible 100 reports 100% utilization. This metric is nearly useless for inference optimization. Use MFU and MBU instead.
MetricDefinitionKey insight
MFU — Model FLOP/s UtilizationActual FLOP/s ÷ Peak FLOP/s of the chipLow during decode (memory-bound). High during prefill. During training, >50% is considered good.
MBU — Model Bandwidth UtilizationActual bandwidth used ÷ Peak bandwidthHigh means you are memory-bound. Calculate: param_count × bytes/param × tokens/s
MBU math example: 7B parameter model, FP16 (2 bytes/param), 100 tokens/s → bandwidth used = 7B × 2 × 100 = 700 GB/s. On an A100 with 2 TB/s peak: MBU = 700/2000 = 35%. Room to improve. Now quantize to INT8 (1 byte/param): bandwidth halves → MBU drops → throughput roughly doubles. That is exactly why quantization works.

import numpy as np
import matplotlib.pyplot as plt
from dataclasses import dataclass

np.random.seed(42)

# ── C-MAPSS Engine Query Simulation ──────────────────────────
@dataclass
class EngineQuery:
    engine_id: str
    input_tokens: int   # 21 sensors × window + system prompt tokens
    expected_rul: float

def generate_queries(n=100):
    return [EngineQuery(
        engine_id=f"ENG-{i+1:03d}",
        input_tokens=int(np.random.normal(21 * np.random.choice([20,30,50]) + 350, 80)),
        expected_rul=np.random.uniform(10, 150)
    ) for i in range(n)]

# ── Inference Simulator ──────────────────────────────────────
def simulate_inference(q, output_tokens=85, overload=False):
    ttft = (q.input_tokens / 500) * 120 + np.random.exponential(20)
    if np.random.random() < (0.25 if overload else 0.05):
        ttft *= np.random.uniform(8, 25)   # tail latency spike
    tpot = max(10, 30 + np.random.normal(0, 5))
    total = ttft + tpot * output_tokens
    return {"ttft_ms": ttft, "tpot_ms": tpot,
            "total_ms": total, "tps": output_tokens / (total / 1000)}

# ── Run + Evaluate ───────────────────────────────────────────
queries  = generate_queries(100)
SLO_TTFT, SLO_TOTAL = 500, 5000

def profile(results):
    ttfts  = [r["ttft_ms"]  for r in results]
    totals = [r["total_ms"] for r in results]
    meets  = [r["ttft_ms"] < SLO_TTFT and r["total_ms"] < SLO_TOTAL for r in results]
    return {"ttft_p50": np.percentile(ttfts,50), "ttft_p99": np.percentile(ttfts,99),
            "total_p99": np.percentile(totals,99), "slo_pct": np.mean(meets)*100,
            "avg_tps": np.mean([r["tps"] for r in results]),
            "goodput": sum(meets)/60, "ttfts": ttfts, "totals": totals}

r_norm = [simulate_inference(q) for q in queries]
r_over = [simulate_inference(q, overload=True) for q in queries]
m_n, m_o = profile(r_norm), profile(r_over)

print("\nC-MAPSS INFERENCE PROFILING RESULTS")
print(f"{'Metric':<25} {'Normal':>10} {'Overload':>10}")
print("-"*48)
for lbl, key in [("TTFT p50 (ms)","ttft_p50"),("TTFT p99 (ms)","ttft_p99"),
                    ("Total p99 (ms)","total_p99"),("Avg TPS","avg_tps"),
                    ("Goodput (req/s)","goodput"),("SLO Pass %","slo_pct")]:
    print(f"{lbl:<25} {m_n[key]:>10.1f} {m_o[key]:>10.1f}")

# ── Visualization ────────────────────────────────────────────
fig, axes = plt.subplots(1,3,figsize=(15,5))
fig.suptitle("NASA C-MAPSS — Inference Service Profiling\nNormal vs. Overload Conditions", fontweight="bold")
# TTFT histogram
axes[0].hist(m_n["ttfts"], bins=25, alpha=.7, label="Normal", color="#00d4ff")
axes[0].hist(m_o["ttfts"], bins=25, alpha=.6, label="Overload", color="#ff6b2b")
axes[0].axvline(SLO_TTFT, color="#ff3d5a", ls="--", lw=2, label=f"SLO {SLO_TTFT}ms")
axes[0].set_xlabel("TTFT (ms)"); axes[0].set_title("Time to First Token Distribution")
axes[0].legend(); axes[0].grid(alpha=.3)
# Latency CDF
pcts = np.arange(1,101)
axes[1].plot(pcts, np.percentile(m_n["totals"],pcts), label="Normal", color="#00d4ff", lw=2)
axes[1].plot(pcts, np.percentile(m_o["totals"],pcts), label="Overload", color="#ff6b2b", lw=2)
axes[1].axhline(SLO_TOTAL, color="#ff3d5a", ls="--", lw=2, label=f"SLO {SLO_TOTAL}ms")
axes[1].axvline(99, color="#ffd700", ls=":", lw=1.5, label="p99")
axes[1].set_xlabel("Percentile"); axes[1].set_title("Total Latency CDF")
axes[1].legend(); axes[1].grid(alpha=.3)
# SLO + Goodput bars
ax = axes[2]
x = np.arange(2); lbls=["Normal","Overload"]
ax.bar(x-.2,[m_n["slo_pct"],m_o["slo_pct"]],.35,label="SLO Pass %",color="#00ff88")
ax.bar(x+.2,[m_n["goodput"]*20,m_o["goodput"]*20],.35,label="Goodput ×20",color="#ff6b2b")
ax.set_xticks(x); ax.set_xticklabels(lbls); ax.set_title("SLO Rate vs Goodput")
ax.legend(); ax.grid(axis="y",alpha=.3)
for c in ax.containers: ax.bar_label(c, fmt="%.1f", padding=2)
plt.tight_layout(); plt.savefig("cmapss_profile.png",dpi=150,bbox_inches="tight"); plt.show()

Under overload, watch the SLO pass rate collapse and goodput drop — not because throughput dropped, but because more requests missed the latency target. PART 04

Model-Level Optimization

⏱ ~8 minutes

Model-level optimization modifies the model itself to make it faster or cheaper. The key tradeoff: some of these techniques change model behavior. Unlike service-level optimizations, they require direct model engineering, not just infrastructure changes.

Reduce numerical precision to shrink the model and increase throughput. The most popular approach — easy, works out of the box for most models, extremely effective. The MBU math explains exactly why it works: halving bytes/param halves bandwidth consumption, which doubles throughput on memory-bound decode.

PrecisionBytes/param7B model sizeMemory reductionTypical decode speedup
FP32428 GBbaseline1×
FP16 / BF16214 GB50%~2×
INT817 GB75%~3–4×
INT40.53.5 GB87%~6–8× (some quality loss)
For your C-MAPSS system: FP16 quantization halves memory footprint, doubles throughput, and fits the model on a cheaper GPU tier. INT8 pushes further but requires validation that RUL prediction precision is maintained — a safety-critical concern worth careful evaluation.

Use a small, fast "draft model" to propose K tokens at a time. The large target model verifies the entire batch in parallel (verification is parallelizable, unlike generation). If draft tokens are accepted — you generated K tokens in the time it takes to generate 1.

DeepMind's implementation for Chinchilla-70B: 4B draft model, 8× faster per token, cut overall latency by more than half, zero quality loss. Can be done in 50 lines of PyTorch. Now built into vLLM, TensorRT-LLM, llama.cpp.

ISE fit: Your structured JSON work order generations are ideal for speculative decoding. The draft model correctly predicts field names and common values. High acceptance rates. Significant TPOT improvement on structured outputs.
When it does not work: Creative or unpredictable text — low acceptance rates mean verification overhead with no benefit. Also: if your MFU is already maxed, the idle FLOPs assumption breaks down.

Every attention computation requires key and value vectors for all previous tokens. Without caching, you recompute them from scratch at every decode step. The KV cache stores them for reuse — you only compute KV vectors for the newest token each step. Essential for any sequence longer than a few dozen tokens.

The memory cost: KV cache size = 2 × B × S × L × H × M (batch × sequence × layers × dimension × bytes). For Llama 2-13B, batch=32, context=2048: the KV cache alone is 54 GB — three times the model weights. Character.AI reduced their KV cache by 20× using attention redesign, removing memory as their primary bottleneck.

PagedAttention (vLLM): manages KV cache in non-contiguous memory blocks like OS virtual memory paging. Reduces fragmentation, enables flexible sharing, enables much larger effective batch sizes. This is why vLLM became dominant.

Distillation: Train a small "student" model to mimic a large "teacher" model. The student matches the teacher's performance on your specific task domain with far fewer parameters. Ideal for ISE use cases requiring a narrow capability at edge-device cost — a distilled bearing-failure classifier running on facility hardware, no cloud required.

Pruning: Remove weights or entire nodes contributing least to predictions. In research: 90%+ parameter reduction while maintaining accuracy. In practice as of 2024: less common than quantization — harder to implement, requires deep architecture knowledge, sparse results not efficiently exploited by all hardware.

PyTorch case study: Llama-7B optimization stack on A100 80GB — compile → INT8 → INT4 → speculative decoding. Each step multiplicative on the previous. Combined: dramatically higher throughput. Real production reference from the PyTorch team, not a benchmark.
PART 05

Service-Level Optimization

⏱ ~10 minutes + Demo 2

Service-level optimization leaves model weights untouched. Quality does not change — only how efficiently you serve requests. This is where most application developers operate, and where the highest-ROI improvements are available right now.

Batching — The Bus System of Inference

If every request gets its own GPU time, you are running a fleet of single-occupancy taxis when you could be running buses. Batching is the most accessible cost-reduction technique.

StrategyHow it worksBest ForKey Tradeoff
StaticWait until batch is full, then processOffline jobs, dev workflowsFirst request waits for last — unbounded wait
DynamicSend on timeout OR when batch fillsProduction with mixed trafficOccasional half-full batches waste compute
ContinuousEject done requests, insert new immediately (Orca method)High-volume LLM servingComplex implementation — use vLLM or TRT-LLM

Prefill / Decode Decoupling

Prefill (compute-bound) and decode (memory-bound) compete for the same GPU resources. Mixing a new prefill job into an active decode batch drains compute from ongoing decodes, spiking TPOT for all active users. Solution: dedicate separate GPU instances to each phase.

Practical ratio for ISE: C-MAPSS queries have medium-length inputs (~500–800 tokens) and medium outputs (~80–120 tokens). A 1:2 prefill-to-decode ratio is a reasonable starting point. Monitor observed TTFT vs. TPOT and adjust. DistServe and "Inference Without Interference" both demonstrate significant improvements from decoupling even with the communication overhead of transferring intermediate states between instances.

Prompt Caching — Pay Once, Reuse Forever

If many queries share overlapping text — like a long system prompt — prompt caching stores the processed version so you compute it only once. The savings compound dramatically at scale.

Without Prompt Cache

500-token system prompt × 10,000 queries/day = 5 million tokens/day computing the same instructions repeatedly.

With Prompt Cache

System prompt computed once. Anthropic: up to 90% cost savings, 75% latency reduction. Gemini: 75% discount on cached input tokens.

Enable this before anything else. If your maintenance advisory chatbot has a 500-token system prompt and handles 10,000 queries/day, prompt caching saves 4.5M input tokens/day. At $15/M for GPT-4o: that is $67/day or ~$24,500/year saved from one configuration change. No model changes. No infrastructure changes.

# ============================================================
# DEMO 2: Batching Strategy Comparison — C-MAPSS Fleet
# Week 6 — AI-Enabled Informatics for Engineers (Rutgers ISE)
# 300-engine fleet, Poisson arrivals, 3 batching strategies
# ============================================================

import numpy as np
import matplotlib.pyplot as plt

np.random.seed(2026)

# ── Parameters ────────────────────────────────────────────────
SYS_TOKENS  = 480    # Maintenance AI system prompt
USER_TOKENS = 650    # 21 sensors × 30 cycles + context
OUT_TOKENS  = 90     # RUL + explanation
IN_COST     = 15.0   # $/1M input tokens
OUT_COST    = 60.0   # $/1M output tokens  (4× input — Anyscale finding)
N_QUERIES   = 900    # 3 queries/engine/hour × 300 engines
SLO_MS      = 5000

# ── Poisson Arrivals ──────────────────────────────────────────
arrivals = np.cumsum(np.random.exponential(3600/N_QUERIES, N_QUERIES))
in_toks  = np.clip(np.random.normal(SYS_TOKENS+USER_TOKENS, 80, N_QUERIES),400,1500)

# ── Cost Functions ────────────────────────────────────────────
def cost_no_cache(it): return (it*IN_COST + OUT_TOKENS*OUT_COST)/1e6
def cost_cached(it):
    return (SYS_TOKENS*IN_COST*0.1 + (it-SYS_TOKENS)*IN_COST + OUT_TOKENS*OUT_COST)/1e6

# ── Static Batching ───────────────────────────────────────────
def static_batch(sz=8):
    lats, costs = [], []
    for i in range(0, N_QUERIES, sz):
        batch_a = arrivals[i:i+sz]; batch_t = in_toks[i:i+sz]
        proc = np.mean(batch_t)/150*1000
        for j in range(len(batch_a)):
            wait = (batch_a[-1] - batch_a[j])*1000
            lats.append(wait + proc + np.random.exponential(100))
            costs.append(cost_no_cache(batch_t[j]))
    return np.array(lats), np.array(costs)

# ── Dynamic Batching ──────────────────────────────────────────
def dynamic_batch(win_ms=500, max_sz=8):
    lats, costs = [], []; i=0
    while i < N_QUERIES:
        t0=arrivals[i]; j=i
        while jand (arrivals[j]-t0)*1000and j-i1
        bt=in_toks[i:j]; proc=np.mean(bt)/150*1000
        for k in range(j-i):
            lats.append(min((arrivals[min(i+k+1,j-1)]-arrivals[i])*1000,win_ms)+proc+np.random.exponential(80))
            costs.append(cost_no_cache(bt[k]))
        i=j
    return np.array(lats), np.array(costs)

# ── Continuous Batching ───────────────────────────────────────
def continuous_batch(cache=False):
    lats=[]; costs=[]
    for it in in_toks:
        lats.append(np.random.exponential(50)+it/200*1000+np.random.exponential(60))
        costs.append(cost_cached(it) if cache else cost_no_cache(it))
    return np.array(lats), np.array(costs)

strategies={
    "Static Batch (sz=8)": static_batch(),
    "Dynamic Batch (500ms)": dynamic_batch(),
    "Continuous (no cache)": continuous_batch(False),
    "Continuous + Cache": continuous_batch(True),
}

print(f"\n{'Strategy':<28} {'p50 ms':>8} {'p99 ms':>8} {'SLO%':>7} {'$/1Kq':>8}")
print("-"*64)
for name,(lats,costs) in strategies.items():
    print(f"{name:<28} {np.percentile(lats,50):>8.0f} {np.percentile(lats,99):>8.0f}"
          f" {np.mean(lats7.1f} {np.mean(costs)*1000:>8.4f}"
          + (" ⭐" if "Cache" in name else ""))

# ── Annual prompt cache savings ───────────────────────────────
daily_q = N_QUERIES * 16
save_per_q = cost_no_cache(np.mean(in_toks)) - cost_cached(np.mean(in_toks))
print(f"\nPrompt Cache Annual Savings: ${save_per_q*daily_q*365:,.0f}/year")
print(f"  (based on {int(daily_q):,} queries/day, {SYS_TOKENS}-token system prompt)")

# ── Plot ─────────────────────────────────────────────────────
fig,axes=plt.subplots(1,3,figsize=(15,5))
fig.suptitle("Batching Strategy Comparison — C-MAPSS 300-Engine Fleet\n"
             "NASA Jet Engine Simulation", fontweight="bold")
names=[n for n in strategies]; clrs=["#ff3d5a","#ffd700","#00d4ff","#00ff88"]
axes[0].boxplot([[strategies[n][0]] for n in names],
               labels=[n.split("(")[0].strip() for n in names],patch_artist=True)
axes[0].axhline(SLO_MS,color="#ff3d5a",ls="--"); axes[0].set_title("Latency (ms)")
axes[0].tick_params(axis="x",rotation=15); axes[0].grid(axis="y",alpha=.3)
s=[np.mean(strategies[n][0]100 for n in names]
b1=axes[1].bar([n.split("(")[0].strip() for n in names],s,color=clrs)
axes[1].set_title("SLO Pass Rate %"); axes[1].set_ylim(0,105)
axes[1].tick_params(axis="x",rotation=15); axes[1].grid(axis="y",alpha=.3)
axes[1].bar_label(b1,fmt="%.1f%%",padding=2)
c=[np.mean(strategies[n][1])*1000 for n in names]
b2=axes[2].bar([n.split("(")[0].strip() for n in names],c,color=clrs)
axes[2].set_title("Cost per 1,000 queries ($)")
axes[2].tick_params(axis="x",rotation=15); axes[2].grid(axis="y",alpha=.3)
axes[2].bar_label(b2,fmt="$%.4f",padding=2)
plt.tight_layout(); plt.savefig("cmapss_batching.png",dpi=150,bbox_inches="tight"); plt.show()

The annual savings from prompt caching alone often justifies the engineering effort to implement it. Static batching is only viable for truly offline workloads with no latency SLO. Every production system handling repeated queries against a fixed system prompt should enable prompt caching on day one.
PART 06

The Cost Engineering Perspective

⏱ ~10 minutes + Demo 3

Everything in inference optimization ultimately converts to dollars. Build the cost intuition now — before your system is in production and the bill is already running.

The Output Token Cost Surprise

From Anyscale's production data: A single output token has approximately the same impact on latency as 100 input tokens. Across API providers, output tokens cost 2–4× more than input tokens. Every word your AI generates costs significantly more than every word it reads. This has direct design implications: verbose outputs are not just bad UX — they are expensive.

# ============================================================
# DEMO 3: Full Cost Model + ROI — C-MAPSS Predictive Maintenance
# Week 6 — AI-Enabled Informatics for Engineers (Rutgers ISE)
# Optimization stacks + ROI vs. unplanned engine removal cost
# NASA C-MAPSS: 21 sensors, 4 operating conditions, 6 fault modes
# ============================================================

import numpy as np
import matplotlib.pyplot as plt
from dataclasses import dataclass

# ── Fleet + Cost Specification ────────────────────────────────
@dataclass
class FleetSpec:
    n_engines:              int   = 300
    queries_per_day:        int   = 4800   # 16/engine/day
    sys_prompt_tokens:      int   = 480
    user_tokens:            int   = 650
    output_tokens:          int   = 95
    cost_per_1m_in:         float = 15.0
    cost_per_1m_out:        float = 60.0
    unplanned_removal_cost: float = 500_000  # $ per event
    planned_removal_cost:   float = 120_000  # $ scheduled overhaul
    unplanned_per_year_no_ai: int = 8
    unplanned_per_year_ai:    int = 2         # conservative estimate

spec = FleetSpec()

# ── Optimization Stacks ───────────────────────────────────────
stacks = {
    "Baseline\n(No optimization)": {
        "cache_discount":   0.0,
        "throughput_mult":  1.0,
        "ttft_factor":      1.0,
        "color": "#ff3d5a",
        "desc": "Raw API calls, no caching, no batching"
    },
    "Stack 1\n(Cache + Batch)": {
        "cache_discount":   0.90,
        "throughput_mult":  2.5,
        "ttft_factor":      0.75,
        "color": "#ffd700",
        "desc": "Prompt caching + continuous batching"
    },
    "Stack 2\n(+INT8 Quant)": {
        "cache_discount":   0.90,
        "throughput_mult":  4.5,
        "ttft_factor":      0.55,
        "color": "#00d4ff",
        "desc": "+ INT8 weight quantization (2× bandwidth)"
    },
    "Stack 3\n(+Speculative)": {
        "cache_discount":   0.90,
        "throughput_mult":  7.0,
        "ttft_factor":      0.40,
        "color": "#00ff88",
        "desc": "+ Speculative decoding (structured JSON output)"
    },
}

def daily_cost(s):
    cached_in = spec.sys_prompt_tokens * (1 - s["cache_discount"])
    fresh_in  = spec.user_tokens
    in_cost   = (cached_in + fresh_in) * spec.cost_per_1m_in / 1e6
    out_cost  = spec.output_tokens * spec.cost_per_1m_out / 1e6
    return (in_cost + out_cost) * spec.queries_per_day

def est_ttft_ms(s, base=350): return base * s["ttft_factor"]
def est_tpot_ms(s, base=28):  return base / (s["throughput_mult"] / 2)

# ── Print Results ─────────────────────────────────────────────
print("\nC-MAPSS FLEET OPTIMIZATION STACK ANALYSIS")
print(f"{'Stack':<26} {'Daily $':>9} {'Annual $':>10} {'TTFT ms':>8} {'TPOT ms':>9}")
print("-"*65)
annual_costs = {}
for name, s in stacks.items():
    dc = daily_cost(s); ac = dc * 365
    annual_costs[name] = ac
    print(f"{name.replace(chr(10),' '):<26} {dc:>9.2f} {ac:>10.0f} "
          f"{est_ttft_ms(s):>8.0f} {est_tpot_ms(s):>9.1f}")

# ── ROI Analysis ──────────────────────────────────────────────
prevented  = spec.unplanned_per_year_no_ai - spec.unplanned_per_year_ai
avoidance  = prevented * (spec.unplanned_removal_cost - spec.planned_removal_cost)
best_stack = list(annual_costs.values())[-1]
net_roi    = avoidance - best_stack
roi_ratio  = avoidance / best_stack if best_stack > 0 else 0

print(f"\nROI ANALYSIS — PREDICTIVE MAINTENANCE VALUE")
print(f"  Prevented unplanned removals/year:  {prevented}")
print(f"  Cost avoidance (unplanned→planned): ${avoidance:>12,.0f}")
print(f"  AI system cost (Stack 3/year):      ${best_stack:>12,.0f}")
print(f"  Net annual ROI:                     ${net_roi:>12,.0f}")
print(f"  ROI ratio: {roi_ratio:.0f}:1 — every $1 in AI returns ${roi_ratio:.0f}")

# ── Visualization ─────────────────────────────────────────────
fig, axes = plt.subplots(1, 3, figsize=(15, 5))
fig.suptitle("Optimization Stack Analysis — C-MAPSS Predictive Maintenance\n"
             "Cost, Latency, and ROI at 300-Engine Scale", fontweight="bold")
names  = list(stacks.keys())
colors = [s["color"] for s in stacks.values()]
lbls   = [n.replace("\n", " ") for n in names]

# Annual cost waterfall
b1 = axes[0].bar(lbls, [daily_cost(s)*365 for s in stacks.values()], color=colors)
axes[0].set_title("Annual Inference Cost ($)")
axes[0].tick_params(axis="x", rotation=12); axes[0].grid(axis="y", alpha=.3)
axes[0].bar_label(b1, fmt="$%.0f", padding=2, fontsize=8)

# TTFT comparison
ttfts = [est_ttft_ms(s) for s in stacks.values()]
b2 = axes[1].bar(lbls, ttfts, color=colors)
axes[1].axhline(500, color="#ff3d5a", ls="--", label="SLO 500ms")
axes[1].set_title("Estimated TTFT (ms)"); axes[1].legend()
axes[1].tick_params(axis="x", rotation=12); axes[1].grid(axis="y", alpha=.3)
axes[1].bar_label(b2, fmt="%.0fms", padding=2, fontsize=8)

# ROI breakdown
roi_cats = ["Unplanned Removal\nSavings", "AI System\nCost (Stack 3)", "Net Annual\nROI"]
roi_vals = [avoidance, best_stack, net_roi]
roi_clrs = ["#00ff88", "#ff3d5a", "#00d4ff"]
b3 = axes[2].bar(roi_cats, roi_vals, color=roi_clrs)
axes[2].set_title("Annual ROI Analysis ($)")
axes[2].grid(axis="y", alpha=.3)
axes[2].bar_label(b3, labels=[f"${v:,.0f}" for v in roi_vals], padding=2, fontsize=9)

plt.tight_layout()
plt.savefig("cmapss_roi.png", dpi=150, bbox_inches="tight")
plt.show()
print("✅ Demo 3 complete")

The ISE Bottleneck Test — answer these three questions:
1. If my system responded instantly but cost 10× more, would my stakeholders accept it? If yes → latency is tighter than cost.
2. If my system was free but took 30 seconds per response, would operators use it? If no → latency is the binding constraint.
3. Does the system perform identically under 5 concurrent users and 50? If not → reliability is where to look first.

Parallelism for Reliability and Scale

When optimization techniques at the model and service level are not enough, you scale horizontally. The most impactful and practical strategy for most ISE teams: replica parallelism — multiple independent copies of your model serving different requests simultaneously. More copies means more concurrent requests handled means lower latency per user at peak load. The tradeoff is proportional hardware cost.

Tensor Parallelism

Splits the model's weight matrices across multiple GPUs — enables models that do not fit on one GPU, and reduces per-request latency. The most common approach for inference. Implemented via vLLM, TensorRT-LLM — select via configuration, no manual implementation required for most teams.

Pipeline Parallelism

Splits model computation into stages across machines. Enables very large models. Adds communication overhead per request — typically avoided for latency-critical inference, preferred for training throughput. If your system is latency-bound, use replica or tensor parallelism first.

For most ISE project teams right now: The correct answer to "which parallelism strategy?" is "none yet." Optimize at the service level first (caching, batching, routing). Only reach for parallelism when you have measured that service-level techniques have been exhausted and you still cannot meet your SLO at your target query volume. Pre-optimization parallelism is expensive, complex, and often masks problems that cheaper fixes would solve.

SUMMARY

Five Things to Carry Out of Week 6

① Diagnose Before You Optimize

Profile first. Are you compute-bound or memory-bound? Measure TTFT, TPOT, goodput, MBU. The bottleneck determines the fix. Applying the wrong technique wastes engineering time and sometimes makes things worse.

② Decode is the Bottleneck

For most LLM applications, autoregressive decode (memory bandwidth-bound, sequential) is slower and more expensive per token than prefill. Quantization, speculative decoding, and KV cache optimization all target this phase. This is where your operator is waiting.

③ Enable Prompt Caching First

If you have a system prompt (you do), prompt caching is the single highest-ROI optimization available with zero model changes. Anthropic: 90% cost savings. Gemini: 75% discount. Takes hours to implement. Saves thousands per year at production scale.

④ Route by Latency Tolerance

Every query does not need the same API tier. Real-time alerts → online API. Nightly fleet reports → batch API at 50% cost. Designing explicit routing between these two endpoints is one configuration change that can cut your monthly batch workload cost in half immediately.

⑤ The ROI of ISE AI is in the Decisions, Not the API Bill: For safety-critical industrial systems, the value of accurate, timely predictions almost always exceeds the cost of running the AI system by an order of magnitude or more. Optimize to keep the system fast enough to be used. The cost of inference is a rounding error next to the cost of a missed failure or an unplanned shutdown.

Common Mix-UpThe Correct Distinction
"nvidia-smi says 95% GPU utilization, we're good"nvidia-smi % measures time active, not efficiency. A GPU doing 1 op/s out of 100 possible reports 95% if it's "active." Use MFU and MBU instead. 95% nvidia-smi utilization means nothing without knowing the theoretical peak.
"Throughput went up, so the system improved"Throughput and goodput are different. Higher throughput with larger batches often means more requests violate your latency SLO. Goodput (requests/s meeting SLO) is what matters for user experience. Always check both.
"We're compute-bound so we need more GPUs"More GPUs helps if you're compute-bound. But most LLM decode workloads are memory bandwidth-bound — adding more compute does not help if data cannot be moved fast enough. Diagnose which you are before buying hardware.
"Quantization will hurt my model quality"FP16 and INT8 weight-only quantization typically show negligible quality degradation for most tasks. Quality degradation becomes significant below INT4. Always validate against your specific task and evaluation set — do not assume degradation without measuring it.
"The batch API is slower so it's worse"For workloads where latency does not matter (nightly reports, offline analysis), batch API at 50% cost is strictly better. Slower is only worse when your use case requires real-time response. Design explicit routing between online and batch for different query types.
"Prompt caching saves input tokens — but output is what's expensive"Both matter. System prompt caching primarily reduces repeated input token costs. But by lowering TTFT (the prefill takes less work), it also helps throughput — allowing the decode phase to start sooner and the GPU to begin the expensive output generation step more quickly.
