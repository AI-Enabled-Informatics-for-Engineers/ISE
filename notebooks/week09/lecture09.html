📖 Week 9 Lecture

Embeddings + Semantic Retrieval as Informatics

Chapter 6, Huyen — RAG and Agents (retrieval portion). The question this week: how do we give a language model the right information, not just any information?

🎯 1 — Why Retrieval Exists: Context as Feature Engineering

Huyen opens Chapter 6 with a precise framing: a model needs both instructions (how to do something) and context (the specific information needed to do it for this query). Instructions are shared across all queries. Context is query-specific. RAG is the discipline of constructing that query-specific context systematically.

Key analogy: Context construction for foundation models is equivalent to feature engineering for classical ML. Both serve the same purpose — giving the model the information it needs to process a specific input correctly.

Won't long context windows make RAG obsolete?

A common question as models reach 128K, 1M, and even 10M token context windows. Huyen's answer is no — for three reasons:

    • Data always grows faster than context windows. Users generate data; they rarely delete it. No context window will ever be large enough for arbitrary applications.
    • Attention degrades on very long contexts. "Lost in the middle" — models systematically pay less attention to information in the middle of long contexts. Stuffing everything in isn't the same as attending to it.
    • Cost and latency scale with tokens. Every extra context token costs money and adds latency. RAG ensures only the most relevant information is in context per query.
Anthropic's guidance: For Claude models, if your knowledge base is smaller than ~200,000 tokens (about 500 pages), you can include the whole thing in the prompt without RAG. Above that threshold, or for dynamic data, RAG is the right architecture.

🏗 2 — RAG Architecture: The Two Pipelines

A RAG system has two fundamental components that operate in two distinct time frames:

📥
Indexing Pipeline (offline / ahead of time)

Process source documents → chunk them into manageable units → convert chunks to embeddings → store embeddings in a vector database. This runs once, or incrementally as data changes.

⚡
Query Pipeline (online / real time)

Receive user query → optionally rewrite it → embed the query using the same embedding model → search the vector database for the k nearest chunks → assemble context → feed into the generative model → return response.

The quality of the entire RAG system depends most heavily on the retriever — the component responsible for indexing and querying. A perfect generator cannot compensate for a retriever that fetches irrelevant documents. As we saw in Week 8, this is why high retrieval P@5 with low factual consistency is such a diagnostic signal: you can have excellent retrieval and still get hallucinations (from the generator), but you cannot get accurate responses if retrieval is poor.

🔤 3 — Term-Based vs. Embedding-Based Retrieval

The Fundamental Problem with Keywords

Term-based retrieval — querying by keyword matching — has powered search engines for decades. It works well out of the box and is extremely fast. But it operates at the lexical level: it matches the surface form of words, not their meaning.

Query "transformer architecture" with term-based retrieval. You'll retrieve documents about neural networks, electrical transformers, and the Transformers movie franchise with equal enthusiasm. The algorithm has no notion of intent.

More fundamentally: a user asking "how do I fix a segfault?" and a document saying "debugging memory access violations in C" have zero lexical overlap, but are semantically identical. Term-based retrieval misses this entirely.

TF-IDF and BM25 — The Classic Baseline

Despite their limitations, term-based methods remain important. TF-IDF (Term Frequency–Inverse Document Frequency) scores documents by how often a query term appears in them (TF), weighted by how rare that term is across the entire corpus (IDF). Common words like "the" get near-zero IDF; rare terms like "EADDRNOTI" get high IDF.

BM25 (Okapi BM25, 25th iteration of Best Matching) is the production-grade evolution of TF-IDF. It normalizes term frequency by document length — preventing long documents from automatically scoring higher just because they contain more words. BM25 and its variants are still widely used and serve as the mandatory baseline to beat when evaluating semantic retrieval.

Production insight: Never deploy semantic-only retrieval without benchmarking it against BM25 first. Many teams have been surprised to find BM25 competitive or superior for their specific domain, especially for technical queries with precise terminology.

Embedding-Based (Semantic) Retrieval

Embedding-based retrieval converts both documents and queries into dense vectors — real-valued coordinates in a high-dimensional space (typically 384–4096 dimensions). Critically, the geometry of this space is trained to reflect semantic relationships: similar meanings end up close together, dissimilar meanings end up far apart.

This is what makes semantic retrieval powerful: "fix segfault" and "debug memory access violation" will have nearby embeddings, while "segfault" and "transformer (electrical device)" will be far apart even though they share vocabulary with other computer science terms.

1
Embed all documents at index time

Run each chunk through an embedding model (e.g., text-embedding-3-small, BAAI/bge-m3, sentence-transformers). Store the resulting vectors in a vector database.

2
Embed the query at query time

Convert the user's query to a vector using the exact same embedding model used during indexing. Dimension and model must match, or distances are meaningless.

3
Find the k nearest vectors

Search the vector database for the k document vectors closest to the query vector, using cosine similarity or L2 distance. Return the corresponding document chunks.

📐 4 — Embeddings as Geometry: What "Meaning" Looks Like in Math

An embedding is a vector — a point in a high-dimensional space. What makes embeddings useful is that the space is structured: distances between points correspond to semantic relationships. This isn't magic; it emerges from training on large text corpora where co-occurrence patterns encode meaning.

The Classic Result: King − Man + Woman ≈ Queen

Word2Vec (Mikolov et al., 2013) first demonstrated that vector arithmetic can capture semantic relationships. The famous example: the vector for "King" minus "Man" plus "Woman" lands near the vector for "Queen." The geometry of the embedding space encodes the concept of royalty independently of gender.

Modern sentence and document embeddings generalize this idea from words to entire passages. The embedding for "I couldn't connect to the database" will be geometrically close to "connection refused error from PostgreSQL" even though they share almost no vocabulary.

Measuring Similarity: Cosine vs. L2

Two vectors are "close" by one of two standard metrics. Cosine similarity measures the angle between vectors — it captures directional similarity regardless of magnitude. This is standard for text embeddings, where the scale of the vector matters less than its direction. L2 (Euclidean) distance measures straight-line distance — it cares about both direction and magnitude. FAISS supports both; cosine is usually the right choice for semantic retrieval of text.

The "Meaning" Problem — What Embeddings Miss

This is the Week 9 discussion topic, and it's genuinely important. Embeddings capture distributional semantics — patterns of co-occurrence in training data. But that is not the same as meaning in a philosophical sense. Several systematic gaps:

Gap 1
Antonyms cluster together
"hot" and "cold" appear in similar contexts, so they end up nearby in embedding space. Embeddings struggle to encode negation and opposition reliably.
Gap 2
Exact symbols are lost
Error codes like EADDRNOT​AVAIL, product SKUs, part numbers, and version strings have embeddings that reflect surrounding text — not the symbol itself. BM25 handles these better.
Gap 3
Cultural & temporal bias
Embeddings encode the associations dominant in training data. "Doctor" may cluster closer to male names; "software engineer" may cluster closer to "young." These biases are inherited, not chosen.
Gap 4
No compositionality guarantee
"The patient recovered quickly" and "The patient did not recover quickly" may have similar embeddings — the model has seen both patterns. Sentence-level negation is notoriously poorly captured.
Gap 5
Domain shift
A general-purpose embedding model trained on web text may encode "RAG" as "ragdoll" or "rags to riches" — not "retrieval-augmented generation." In-domain finetuning is often necessary.
Gap 6
No world knowledge
Embeddings encode linguistic patterns, not facts. "The capital of France" and "Paris" will be related — but this relationship comes from co-occurrence, not from genuinely knowing that Paris is the capital.

⚡ 5 — Vector Search at Scale: Approximate Nearest Neighbors

Naive k-NN — compare every query vector to every stored vector, rank by similarity, return top-k — is exact but O(n) per query. At 10 million documents it's impractically slow. The solution is Approximate Nearest Neighbor (ANN) search: trade a small amount of accuracy for massive speed gains.

For most applications under 10M vectors, HNSW is the right default — it's what both Chroma and FAISS default to for small-to-mid scale deployments.

✂️ 6 — Chunking Strategy: The Underrated Decision

How you split source documents into retrievable chunks is one of the most practically impactful decisions in a RAG pipeline — and one of the least glamorous. Chunk size affects recall, precision, context quality, and cost simultaneously.

📄 Chunking Approaches — Visual

The transformer architecture introduced self-attention, enabling models to weigh the relevance of different parts of the input. This mechanism allows the model to process sequences in parallel rather than sequentially, dramatically reducing training time. Attention weights reflect the model's focus on specific tokens when generating each output token, providing a form of interpretability.

Strategy 1
Fixed Size
Split every N characters / words / sentences. Simple and fast. Risk: cuts mid-thought. Use overlap to mitigate boundary loss.
Strategy 2
Recursive Splitter
Try section → paragraph → sentence → word in order. Stop when chunk fits. Preserves natural boundaries much better than fixed size.
Strategy 3
Semantic Splitter
Use embeddings to detect topic shifts. Split when cosine similarity between adjacent sentences drops below threshold. Computationally expensive but high-quality chunks.
Strategy 4
Contextual Retrieval
Anthropic's approach: prepend a 50-100 token AI-generated context summary to each chunk before indexing. Makes isolated chunks self-contained and dramatically improves retrieval recall.
Chunk size tradeoffs: Smaller chunks → more diverse information, fits more per context, but loses long-range dependencies and doubles your vector storage if you halve size. Larger chunks → richer context per result, but may dilute relevance and hit model context limits. There is no universal optimal — experiment with your specific documents and query distribution.

🔀 7 — Hybrid Search, Reranking & Query Rewriting

Hybrid Search + Reciprocal Rank Fusion (RRF)

Run term-based and semantic retrievers in parallel. Each returns a ranked list. Merge them using RRF: each document's score is the sum of 1/(k + rank_i) across all ranked lists, where k=60 is a smoothing constant. Documents consistently ranked highly by multiple retrievers rise to the top; no single retriever's quirks dominate.

Hybrid search gets you the best of both worlds: term-based precision for exact keywords (error codes, product IDs, proper nouns) and semantic recall for natural language intent and paraphrases.

Reranking

The initial ranked list from the retriever can be improved with a second-pass reranker. The pattern: use a fast, approximate retriever (BM25 or ANN) to get 100 candidate chunks. Then apply an expensive but precise cross-encoder model that jointly considers the query and each candidate chunk together (rather than comparing embeddings independently) to produce a final top-10. Cross-encoders are slower but more accurate because they can model interaction between query and document explicitly.

Documents can also be reranked by recency — essential for news aggregation, email Q&A, or any time-sensitive application where the most recent information should be prioritized over older, possibly more topically similar content.

Query Rewriting

Multi-turn conversations produce ambiguous queries. "How about Emily Doe?" means nothing in isolation — but in context, it means "When was the last time Emily Doe bought something from us?" A query rewriting step uses the conversation history to reformulate the raw user input into a self-contained query before passing it to the retriever.

This can be done with heuristics for simple cases (replace pronouns with their referents) or with a small LLM call for complex coreference resolution and entity expansion.

📊 8 — Evaluating Retrieval: What to Measure

Retrieval quality must be measured at three levels — the retriever alone, the embeddings alone, and the end-to-end RAG system output — because failures can occur at any layer independently.

Context PrecisionOf retrieved docs, what fraction are relevant?AI judge labels each retrieved chunk; mean across queries

Evaluation architecture: Measure retrieval precision and generation faithfulness separately. This isolation is what tells you whether a system failure is a retrieval problem (wrong chunks) or a generation problem (hallucinating despite good chunks). You cannot diagnose the system if you only measure end-to-end output.

🌐 9 — Beyond Text RAG: Multimodal and Tabular

Multimodal RAG

When the generator is multimodal (e.g., GPT-4V, Gemini), context can include images, audio, and video alongside text. CLIP (Contrastive Language-Image Pre-training, Radford et al. 2021) enables joint embedding of images and text in the same vector space — you can embed a text query and retrieve images by cosine similarity.

Tabular RAG — Text-to-SQL

Many real queries require structured data — sales figures, user records, inventory counts. The workflow: (1) text-to-SQL model converts natural language to a SQL query using the table schema as context; (2) execute the SQL query against the database; (3) include the result in the generative model's context. This is conceptually a form of RAG where the "retriever" is a SQL executor and the "index" is a relational database.

-- Generated by text-to-SQL from: "How many units of Fruity Fedora sold in last 7 days?" SELECT SUM(units) AS total_units_sold FROM Sales WHERE product_name = 'Fruity Fedora' AND timestamp >= DATE_SUB(CURDATE(), INTERVAL 7 DAY);
