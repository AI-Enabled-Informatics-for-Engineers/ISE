📖 Week 10 Lecture

RAG Systems: Grounding + Evaluation

Week 9 asked: how do we retrieve the right information? Week 10 asks: how do we verify the model is actually using it — and build the machinery to prove it?

🔄 1 — The Full RAG Pipeline: From Retrieval to Answer

Week 9 covered the retrieval half of RAG in depth — how embeddings encode meaning, how ANN indexes scale, how hybrid search and reranking improve recall. This week we take the output of that retrieval and ask: what actually happens next?

The pipeline after retrieval has three critical steps that are often underspecified in tutorials but where the most dangerous failure modes live:

1
Context Assembly

The retrieved chunks are formatted into a structured prompt context. This is not trivial — chunk ordering matters (models attend better to information at the beginning and end of context), chunk count must fit the context window, and metadata like source citations should be included for attribution.

2
Grounded Prompt Construction

The system prompt must explicitly constrain the model to the provided context. Without an explicit grounding instruction, models freely mix retrieved evidence with parametric knowledge — and they do so confidently and fluently, making hallucinations indistinguishable from grounded answers.

3
Generation + Attribution

The model generates a response. Ideally, it cites the specific chunks that support each claim. The generated response then goes through an evaluation layer before being served — or the evaluation runs asynchronously on a sample of production traffic.

The central insight of Week 10: A RAG system can have perfect retrieval (P@5 = 1.0) and still hallucinate — if the generation step is not properly grounded and evaluated. The retrieval and generation components fail independently. You need evaluation machinery that measures both.

⚓ 2 — Grounding: What It Means and How to Enforce It

Grounding is the property of a generated response that all factual claims in it are supported by (entailed by) the provided retrieved context — not by the model's parametric knowledge. A grounded system says "I don't know" or "the provided context doesn't address this" when the retrieved chunks don't contain the answer. An ungrounded system fills in the gap from training data, often with high confidence.

The Grounding Spectrum

Fully Ungrounded
Pure Parametric
Model answers entirely from training data. No retrieved context used. Standard LLM behavior. Hallucination rate highest here.
Partially Grounded
Mixed Sources
Model blends retrieved context with parametric knowledge. Most common failure mode in RAG — the context is present but the model supplements it. Subtle and dangerous.
Fully Grounded
Context-Anchored
All claims traced to retrieved chunks. Model refuses to answer questions not addressable from context. Maximum faithfulness, minimum hallucination.

The Grounding System Prompt Pattern

The single most impactful engineering change for improving grounding is the system prompt. Here is the pattern that consistently outperforms generic prompts in production:

# The grounding system prompt — use this pattern SYSTEM_PROMPT = """You are a precise, evidence-based assistant. RULES (follow these strictly): 1. Answer ONLY using information from the CONTEXT section below. 2. If the context does not contain enough information to answer, say: "The provided context does not address this question." 3. Do NOT use your pre-trained knowledge to supplement the context. 4. For every factual claim, cite the source chunk (e.g., [Source 1]). 5. If chunks contain conflicting information, flag the conflict explicitly. CONTEXT: {context} QUESTION: {question} Answer based only on the context above:"""
Why explicit rules beat implicit instructions: Models are trained to be helpful. Without explicit prohibition, they default to supplementing incomplete context with training knowledge — which feels helpful but introduces unverifiable claims. The numbered rules force the model to acknowledge knowledge boundaries rather than paper over them.

Citation and Attribution Patterns

Grounding becomes verifiable when the model cites the specific chunk each claim comes from. This has two engineering benefits: users can verify claims by clicking through to sources, and your evaluation harness can check whether cited chunks actually entail the claims.

# Formatted context with citation markers def format_context_with_citations(chunks: list[dict]) -> str: context_parts = [] for i, chunk in enumerate(chunks, 1): context_parts.append( f"[Source {i}] {chunk['metadata']['source']}\n" f"{chunk['content']}\n" ) return "\n---\n".join(context_parts) # Instruct model to cite inline: "The system requires... [Source 2]"

🔴 3 — Hallucination Taxonomy in RAG Systems

Not all hallucinations are the same. In RAG-specific contexts, three distinct failure types occur — and they require different diagnostic approaches and fixes. Understanding the taxonomy is the first step toward targeted remediation.

Type 1
Conflation Hallucination
The model generates a claim that is true in its training data but contradicts the retrieved context. The model substitutes its memory for the provided evidence. Example: context says "released 2023," model says "released 2022" because that's what it learned during training.
Type 2
Intrusion Hallucination
The model introduces a factual claim that is not present anywhere in the retrieved context — neither confirmed nor denied. Pure parametric generation leaking into what should be a grounded response. Example: adding specific numbers, names, or dates not in any retrieved chunk.
Type 3
Completeness Hallucination
The retrieved context partially addresses the question. The model answers the partial question correctly but presents the answer as complete, hiding the gap. Example: context covers only half a procedure; model describes the full procedure confidently, fabricating the missing half.

Diagnostic Question: Which Component Is Failing?

SymptomLikely Root CauseTargeted Fix
High retrieval P@5 + low faithfulnessGeneration: model not grounded to contextStronger system prompt; add grounding constraint
Low retrieval P@5 + low faithfulnessRetrieval: wrong chunks retrieved; generator working with bad evidenceImprove retrieval (Week 9 tools); re-evaluate
High retrieval P@5 + high answer relevance + low faithfulnessIntrusion hallucination: model supplements with parametric knowledgeExplicit "do not use prior knowledge" instruction + entailment checker
Correct answer, no citationAttribution missing; answer may be grounded but unverifiableAdd citation instruction to prompt; validate post-generation
Correct answer for known queries, wrong for novel queriesConflation: model falls back to training data for unknown conceptsDetect via SelfCheckGPT; add abstention instruction

📊 4 — RAGAS: The Four-Metric RAG Evaluation Framework

RAGAS (Retrieval Augmented Generation Assessment) is the most widely adopted framework for evaluating RAG systems end-to-end. It decomposes system quality into four orthogonal metrics, each measuring a distinct failure mode. A system can score well on three and fail catastrophically on the fourth — which is why all four are necessary.

Faithfulness
—
Are all claims in the generated answer entailed by the retrieved context? Measures grounding quality. Low score = hallucination in the generation step.
Answer Relevance
—
Does the generated answer actually address the question asked? Measures response coherence. Low score = answer is grounded but off-topic.
Context Precision
—
Of the retrieved chunks, what fraction are actually relevant to the question? Measures retrieval precision. Low score = noisy retrieval polluting the context.
Context Recall
—
Does the retrieved context contain all the information needed to answer the question? Measures retrieval completeness. Low score = relevant chunks missing from retrieval.
The critical relationship between these four metrics: Faithfulness and Answer Relevance measure the generation component. Context Precision and Context Recall measure the retrieval component. This decomposition is what allows you to diagnose which half of the pipeline is failing — which is the entire point of building an evaluation harness rather than measuring end-to-end accuracy alone.

How Faithfulness Is Computed

Faithfulness is the hardest metric to compute automatically because it requires an entailment judgment — does the retrieved context logically support each claim in the response? The RAGAS implementation uses an LLM-as-judge pattern:

# Faithfulness computation (RAGAS pattern) def compute_faithfulness(answer: str, context_chunks: list[str], judge_llm) -> float: # Step 1: decompose answer into atomic claims claims_prompt = f"""Extract all factual claims from this answer as a list. Answer: {answer} Return only the claims, one per line.""" claims = judge_llm.invoke(claims_prompt).split('\n') # Step 2: for each claim, check if context entails it supported = 0 for claim in claims: entail_prompt = f"""Context: {' '.join(context_chunks)} Claim: {claim} Is this claim fully supported by the context? Answer YES or NO.""" result = judge_llm.invoke(entail_prompt).strip() if "YES" in result.upper(): supported += 1 return supported / len(claims) if claims else 0.0

🏗 5 — Building the Evaluation Harness

An evaluation harness is a systematic, reproducible pipeline for scoring your RAG system across a representative set of test cases. It is the engineering artifact that converts informal testing ("I tried a few queries and it seemed okay") into measurement-backed quality assurance.

The Test Dataset: Your Most Important Asset

The harness is only as good as the test dataset it runs on. A test dataset for RAG evaluation requires four components per test case:

Q
Question

A representative query from your actual user distribution — or a synthetic query generated to probe a specific capability or failure mode.

G
Ground Truth Answer

The correct answer, written by a domain expert based on the source documents. Used to compute answer correctness against a human gold standard.

C
Ground Truth Context

The specific chunks from the corpus that contain the information needed to answer this question. Used to compute context recall — did retrieval find these chunks?

M
Metadata

Query type (factual, multi-hop, adversarial), domain, difficulty level. Enables sliced analysis — do you perform differently on simple factual queries vs. complex reasoning queries?

Harness Architecture

# Assignment 4 skeleton — evaluation harness from ragas import evaluate from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall from datasets import Dataset import pandas as pd class RAGEvaluationHarness: def __init__(self, rag_pipeline, test_dataset: list[dict]): self.pipeline = rag_pipeline self.test_data = test_dataset # list of {question, ground_truth, contexts} def run(self) -> pd.DataFrame: results = [] for case in self.test_data: # 1. Run the RAG pipeline response = self.pipeline.invoke(case['question']) retrieved_chunks = response['source_documents'] answer = response['answer'] # 2. Collect result for RAGAS evaluation results.append({ 'question': case['question'], 'answer': answer, 'contexts': [doc.page_content for doc in retrieved_chunks], 'ground_truth': case['ground_truth'], 'ground_truth_contexts': case['contexts'], }) # 3. Score with RAGAS dataset = Dataset.from_list(results) scores = evaluate( dataset, metrics=[faithfulness, answer_relevancy, context_precision, context_recall] ) return scores.to_pandas()
What the harness tells you: Run this on 20–50 representative test cases. The output DataFrame shows per-query scores on all four metrics. Sort by faithfulness ascending to find your worst-performing queries. Those are your debugging targets — read the retrieved context and the generated answer side-by-side to understand which of the three hallucination types is occurring.

🛡 6 — Guardrails: Preventing Hallucination at the System Level

Evaluation tells you what went wrong. Guardrails try to prevent it. The two-layer approach — prevention at generation time, detection after generation — is more robust than either alone.

Layer 1: Generation-Time Prevention

    • Grounding system prompt — explicit "only use context" instructions (Section 2)
    • Temperature control — lower temperature (0.0–0.3) reduces creative generation that departs from context; appropriate for factual Q&A
    • Context window management — include only the k most relevant chunks, not all of them; irrelevant context increases the probability the model supplements from parametric knowledge to fill perceived gaps
    • Abstention training — fine-tuned models can be trained to say "I don't know" rather than hallucinate; this is a model-level intervention

Layer 2: Post-Generation Detection

    • Entailment checking — run a lightweight NLI (Natural Language Inference) model to check whether each claim in the response is entailed by the context. Fast, cheap, can run synchronously before serving.
    • SelfCheckGPT — for open-domain queries where no ground truth context exists; samples N additional responses and measures internal consistency (from Week 8)
    • LLM-as-judge faithfulness — more accurate than NLI but slower and more expensive; use on a sample of production traffic
    • Citation validation — if the model cites [Source 2], verify that [Source 2] actually entails the cited claim; flag misattributions automatically
# Synchronous entailment guardrail (before serving) from transformers import pipeline nli = pipeline("text-classification", model="cross-encoder/nli-deberta-v3-small") def check_grounded(answer: str, context: str, threshold: float = 0.7) -> dict: result = nli(f"{context} [SEP] {answer}")[0] entailment_score = result['score'] if result['label'] == 'ENTAILMENT' else 1 - result['score'] return { 'grounded': entailment_score >= threshold, 'score': entailment_score, 'action': 'serve' if entailment_score >= threshold else 'flag_for_review' }

🔗 7 — Context Window Management for RAG

One of the most practically important and least discussed challenges in production RAG is context window budget management. Your generative model has a fixed context limit (e.g., 128K tokens for GPT-4o). Your system prompt, conversation history, retrieved chunks, and question all compete for that budget.

The Budget Allocation Problem

Context ComponentTypical Token BudgetNotes
System prompt (grounding rules)200–500 tokensFixed; optimize for minimum needed to achieve grounding
Conversation history0–8,000 tokensVariable; must truncate old turns in long sessions
Retrieved chunks (k chunks)k × chunk_size tokensLargest variable; tune k and chunk_size together
User question10–200 tokensUsually small but adversarial inputs can be long
Output generation budget500–4,000 tokensReserve space for the answer you expect

The practical rule: reserve 30–40% of your context window for the system prompt + question + output. Use the remaining 60–70% for retrieved chunks. If your chunks are 512 tokens each, you can fit about 150 chunks into a 128K window — but you should never retrieve 150 chunks because most will be irrelevant noise. Aim for 5–10 high-precision chunks. More chunks without precision improvement degrades faithfulness.

The lost-in-the-middle effect: Huyen cites research showing that models pay systematically less attention to content in the middle of long contexts. If you stuff 50 chunks into the context, the model effectively ignores most of them. Tighter retrieval + fewer, more relevant chunks consistently outperforms large context with loose retrieval — and is cheaper.

Dynamic Context Assembly

# Context budget manager def assemble_context(chunks: list[dict], budget_tokens: int, tokenizer) -> list[dict]: selected, used = [], 0 for chunk in chunks: # already ranked by relevance chunk_tokens = len(tokenizer.encode(chunk['content'])) if used + chunk_tokens > budget_tokens: break selected.append(chunk) used += chunk_tokens return selected # never exceed budget

🧪 8 — Testing Strategies for RAG Systems

Beyond RAGAS scores on a fixed test set, production RAG systems need three additional testing strategies to catch the failure modes that aggregate metrics miss.

Adversarial Testing

Deliberately craft queries designed to trigger hallucination. The goal is to find the edge of the system's grounding before users do. Categories of adversarial queries:

Type A
Out-of-scope queries
Questions the corpus cannot answer. The grounded system should abstain. An ungrounded system will fabricate.
Type B
Near-miss queries
Questions very similar to answerable queries but with key details changed. Tests whether the model notices the difference or answers based on the similar-but-wrong context.
Type C
Contradictory context
Inject chunks that contradict each other. Does the model flag the conflict or pick one arbitrarily? Grounded systems should surface conflicts explicitly.
Type D
Leading questions
"Confirm that X is the case, even though the actual policy is Y." Tests whether the model resists user pressure to validate incorrect claims.

Regression Testing

Every change to your RAG system — new embedding model, different chunking strategy, updated prompts — should be validated against a fixed regression test suite. Run RAGAS before and after the change. A change that improves faithfulness but degrades context recall is not obviously an improvement. Track all four metrics together over time.

Production Sampling

A 2–5% sample of real production queries, evaluated asynchronously via LLM-as-judge faithfulness checking, provides the ground truth signal that no fixed test set can match. Real users ask questions the test set didn't anticipate. Production sampling catches these distribution shifts before they accumulate into reputational failures.

🔁 9 — Closing the Loop: From Evaluation to Improvement

An evaluation harness without an improvement loop is just diagnostics. The value comes from using scores to drive specific, targeted changes to specific system components.

If This Metric Is LowDiagnose ByImprove By
FaithfulnessRead the low-scoring (query, context, answer) triples; identify which hallucination typeStrengthen grounding prompt; add entailment guardrail; lower temperature
Answer RelevanceCheck if retrieved context is relevant; check if prompt is distracting the modelImprove query rewriting; check system prompt for over-constraining the response
Context PrecisionExamine retrieved chunks for off-topic noiseImprove retrieval (reranker, hybrid search tuning); reduce k; add metadata filtering
Context RecallIdentify which ground truth chunks were missedImprove chunking strategy; tune embedding model; add contextual retrieval
The evaluation flywheel: Build test set → Run harness → Identify lowest metric → Make targeted fix → Re-run harness → Compare deltas → Update test set with new adversarial cases → Repeat. Each cycle moves all four metrics toward 1.0 while revealing new failure modes to address. This is how production RAG systems improve continuously over time.
