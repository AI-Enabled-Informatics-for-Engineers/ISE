📖 Week 11 Lecture

Agentic Workflows + Human Oversight

Six sections. The first half covers how agents work. The second half covers what can go wrong and how to design systems that stay under control.

🔄 1 — From RAG to Agents: What Changes When the Model Acts

In Weeks 9 and 10, the model was a responder. You gave it a question and retrieved context, it generated an answer, you evaluated whether that answer was grounded. The model was passive — every real-world action was still taken by code you wrote.

An agent is different. An agent is a model that can take actions in the world — call a search API, execute a SQL query, write and run code, send an email, book a meeting. The model is no longer just producing text. It is producing decisions that have real effects.

That shift produces a cascade of new engineering challenges. In a RAG system, the worst outcome is a hallucinated answer — the user reads it and asks again. In an agentic system, the worst outcome is a hallucinated action — and by the time you catch it, it may have already executed.

The core distinction: RAG errors are recoverable. Agent errors may not be — a deleted file, a sent email, a submitted order. This asymmetry is the reason human oversight is not optional in agentic systems.

The ReAct Loop — Reasoning + Acting

The most common pattern for agents is ReAct — Reasoning and Acting. The model alternates between thinking (producing a plan or decision), acting (calling a tool), and observing (reading the tool's output). This loop continues until the task is complete.

💭
Think

The model reasons about the task: "To answer this, I need to check inventory. I should query the database."

⚡
Act

The model calls a tool: query_inventory(sku="A-1042", warehouse="NJ-01")

👁
Observe

The tool returns a result: {"stock": 47, "reorder_point": 50, "lead_time_days": 14}

💭
Think again

"Stock is below reorder point. I should trigger a purchase order." The loop continues until the task is complete or a gate is reached.

🏗 2 — Agent Architecture: Tools, Planning, Memory

Huyen's Chapter 6 frames agents around three capabilities the base model lacks on its own.

Tools

Tools are functions the model can call — web search, code execution, database queries, API calls, file operations. The model produces a structured output (typically JSON) describing which tool to call and with what parameters. Your code executes the tool and returns the result. Tool design is one of the most consequential decisions in an agentic system: a poorly scoped tool that can do too much creates risk; a too-narrow tool creates friction that pushes the model toward workarounds.

Planning

For complex multi-step tasks, the agent needs to plan before acting. Patterns include chain-of-thought (reason step-by-step before committing to a tool call), plan-and-execute (generate a full plan, then execute each step), and tree-of-thought (generate multiple candidate plans and evaluate them before proceeding).

Memory

An agent has four memory layers. In-context memory is everything in the current prompt window. External memory is a retrieval system — this is Week 9's architecture applied to agents. Episodic memory stores past interactions retrievable later. Procedural memory is knowledge in the model weights themselves. Most production agents use in-context and external memory.

The context window is the agent's working memory. Every tool result added to context consumes space. A long-running agent loop can exhaust the context window mid-task, corrupting the agent's understanding of where it is. Context window management (Week 10, Section 7) is doubly important for agents.

⚠️ 3 — Agent Failure Modes

Agent failures are structurally different from RAG failures. In Week 10 you built a harness that caught hallucinations before they reached users. For agents, failures can only be caught after they execute. Understanding the taxonomy is the precondition for designing systems that contain them.

Failure 1
Prompt Injection
Malicious content in the environment (a web page, an email) contains instructions that hijack the agent's behavior. Unlike chatbot injection — where the worst outcome is a bad response — an agent can be hijacked into executing real tool calls.
Failure 2
Excessive Agency
The agent has more tool access than the task requires. Given a read task, it decides to also write. Least-privilege tool design is the defense — agents should only have access to what the current task actually needs.
Failure 3
Runaway Loops
The agent gets stuck cycling through tool errors indefinitely. Always implement a maximum iteration count and a cost budget with hard stops.
Failure 4
Cascading Errors
An error in step 3 corrupts the state all subsequent steps depend on. The agent continues confidently on a flawed foundation. Every irreversible action is a potential cascade trigger.
The asymmetry that changes everything: RAG failures are in the output — evaluate, catch, retry. Agent failures can be in side effects — database records written, emails sent, orders placed. Your harness cannot catch a side effect after it happens. Prevention and containment must be designed in before deployment.

🛡 4 — Human Oversight: Approval Gates and Audit Logs

Human oversight in agentic systems is not the same as human oversight in traditional software. You cannot read every output — agents act faster than humans can review. The engineering challenge is designing oversight mechanisms that are effective without eliminating the efficiency gains that make agents worth building.

The Approval Gate Pattern

An approval gate pauses execution and waits for a human to review a proposed action before it executes. The key design decision: which actions require approval?

Action CategoryApproval RequirementWhy
Read-only queriesNoneReversible — reading changes nothing
Low-stakes writes (log, draft)Optional / async reviewLow cost to undo
External communication (email, Slack)RequiredCannot be unsent; creates expectations
Financial transactionsRequired + dual authorizationRegulatory + financial risk
Irreversible operations (delete, deploy)Mandatory + confirmationCannot be undone

The Audit Log Pattern

An audit log records every agent action — what it decided, what tool it called, what parameters it used, what the tool returned, who approved or denied the action, and when. Three functions: debugging (trace what went wrong), accountability (prove what the agent did), and improvement (identify failure patterns).

Minimum viable audit log fields: timestamp, session_id, step_number, action_type, tool_name, parameters, result_summary, risk_level, approval_status, approver_id. In any regulated industry application — healthcare, finance, defense, manufacturing — these are requirements, not options.

Autonomy Calibration

Full automation and full human control are both suboptimal endpoints. The engineering goal is calibrated autonomy: automate where failure cost is low and model accuracy is high; require human review where failure cost is high or model accuracy is uncertain. As you collect audit log data and measure error rates by action type, adjust approval thresholds based on evidence.

🔒 5 — OWASP LLM Top 10: Priority for Agents

The OWASP LLM Top 10 is the security community's consensus on the highest-priority risks in LLM applications. For agentic systems specifically, five are directly and severely relevant. Full reference is on the OWASP tab.

1
Prompt Injection — highest priority

Environmental content the agent retrieves (web pages, emails, documents) may contain adversarial instructions. Unlike chatbot injection, in an agent the injected instruction can trigger real tool calls with real effects. Defense: treat all retrieved content as untrusted data, never as trusted instruction.

8
Excessive Agency — the architectural risk

Too many tools, too broad permissions, too little oversight. Design: grant only what the task needs, for only as long as the task runs. Revoke permissions when the task ends.

2
Insecure Output Handling

Agent tool outputs passed to subsequent tools without sanitization can propagate injections. Sanitize all tool outputs before using them as inputs to the next step.

9
Overreliance

Teams remove human review after observing agents work in testing. The agent then encounters a distribution shift in production and fails without any oversight mechanism. The audit log + approval gate directly counter this.

The M6 deliverable — approval gate and audit log — directly mitigates LLM01, LLM02, LLM08, and LLM09.

⚖️ 6 — What's the Smallest Useful Autonomy?

This is the Week 11 discussion question and it pushes back against the engineer's instinct to maximize automation. "Smallest useful autonomy" reframes the design question: instead of asking how much you can automate, ask what is the minimum level of autonomy that still generates the value that justified building the agent.

A procurement agent that drafts purchase orders for human approval is useful — it saves the cognitive work of writing the order while keeping a human in the loop for the financial commitment. One that also submits the order is more autonomous but adds approval risk. One that also negotiates pricing with suppliers is more autonomous still — but if it negotiates badly, the failure cost may exceed the efficiency gain.

The right answer depends on task reversibility, model accuracy on the task distribution, cost of failure, and organizational capacity for oversight. What makes it interesting to discuss is that there is no universal right answer — only context-specific right answers.

Sensitive Information Disclosure
Model reveals confidential data in responses. Agents with broad database access can inadvertently surface data they were not intended to expose. Audit log is a detection mechanism.

Insecure Plugin Design
Tools with insufficient input validation, excessive permissions, or inadequate authentication. Every tool in an agent's toolkit should be hardened as an attack surface.
🔴 Critical for agents

Excessive Agency
Agent has too much functionality, permissions, or autonomy relative to what the task requires. Mitigation: least-privilege tool design + scoped permissions + mandatory approval for high-risk actions.
🔴 Critical for agents
LLM09
Overreliance
Excessive trust in model output without sufficient validation. The audit log + approval gate directly counter this risk by creating a record of what the agent did and requiring human review of high-risk actions.

LLM10
Model Theft
Unauthorized copying or replication of a proprietary model via API queries or side-channel attacks. Primarily relevant for organizations deploying proprietary fine-tuned models.

A gate that classifies proposed actions by risk level and routes them: LOW = auto-proceed, MEDIUM = flag for async review, HIGH = block and wait for explicit approval.

Component 2 — Audit Log

Captures every agent action — proposed and executed. Must answer: "What did the agent do?" and "Were any actions denied?"

  • □AuditLog class with log() and summary() methods
  • □Required fields: timestamp, step, action_type, tool, parameters, risk_level, status, notes
  • □Export to CSV or JSON
  • □At least one DENIED entry in the log
